# Architecture

## Repository and initialized stack

The repository has a minimal Next.js App Router foundation under `src/app`. The initialized stack is **Next.js 16.4.2 + React 19.3.1 + TypeScript 5.9.3 (strict) + Tailwind CSS 4.3.3 + ESLint 9.39.5**, managed with npm and Node.js 24 (`engines.node: ">=24 <25"`). The package lock records the resolved dependency tree.

PostgreSQL access is configured with **Prisma ORM 7.10.1**, `@prisma/client`, the `@prisma/adapter-pg` driver adapter, and `pg`. Local development uses the locally installed native PostgreSQL server. The schema is at `prisma/schema.prisma`; the generated client is at `src/generated/prisma` and is regenerated with `npm run prisma:generate`. The schema implements Organization, Client, ClientContact, and Service. The initial migration is `20261020151624_init_master_data`.

The production database strategy remains undecided until deployment. The server-only reusable client is exposed through `getPrismaClient()` in `src/lib/prisma.ts`. It is initialized lazily when called, checks for `DATABASE_URL`, and does not connect during module import. Store the URL only in the server environment or an ignored `.env` file; never expose it to client code. `.env.example` contains placeholders only.

Production authentication identity is verified in server-only `src/lib/auth/identity.ts`: the request's `Cf-Access-Jwt-Assertion` is verified with `jose` using Cloudflare Access public JWKS, the configured team issuer, and configured audience. The verified email is normalized and mapped to an existing active `User`; identities do not auto-provision. `DEV_AUTH_EMAIL` is a server-only local development identity and cannot be used in production. Server-only `src/lib/auth/authorization.ts` loads active organization memberships and applies a centralized typed ADMIN/BILLING/VIEWER permission matrix. Production app routes should obtain organization access through these helpers before invoking tenant-scoped services. The application does not implement password login or MFA; Cloudflare Access is responsible for the mandatory MFA policy and the deployment must prevent direct origin bypass.

The production invoice workspace lives at `/app`, `/app/[organizationSlug]/invoices/new`, `/app/[organizationSlug]/invoices/[invoiceId]/edit`, `/app/[organizationSlug]/invoices/[invoiceId]/preview`, and `/app/[organizationSlug]/invoices/[invoiceId]`. `/app` uses the authenticated user's active memberships to redirect a single-organization user or list only their permitted organizations. A route slug is a selector only: `requireOrganizationBySlug()` resolves it by searching that user's active memberships, checks the requested permission, and returns the trusted `organizationId`. Production search, save, and issue Server Actions repeat this resolution and permission check on every call; they do not accept an organization ID from the client. Creation calls `createDraftInvoice()` and editing calls the atomic `updateFullDraftInvoice()` service. Draft preview is a read-only `INVOICE_EDIT_DRAFT` operation using the current active default template and current client details, explicitly labeled as an unfrozen preview. Issuance requires `INVOICE_ISSUE` and calls the transactional `issueInvoice()` service.

Invoice issuance is implemented in the server-only domain module `src/lib/invoices/issue-invoice.ts`. It loads and validates a draft within its organization, resolves and validates the latest version of that organization's active default invoice template before sequence reservation, recalculates line and invoice totals, snapshots current client details, reserves the organization's next number atomically, and commits the version binding, invoice, and sequence update in one PostgreSQL transaction. Future server actions or API handlers must supply organization scope from trusted authorization context.

Draft invoice creation and editing live in the server-only `src/lib/invoices/draft-invoice.ts` service. It validates active organization-owned clients and services, calculates line and invoice totals with the same shared Decimal helpers used by issuance, and uses invoice row locks plus transactions for draft mutations. Drafts remain unnumbered and unbound to a template version. `issueInvoice()` independently recalculates totals and takes the same invoice row lock before reading, serializing issuance with concurrent draft edits.

Invoice items store an explicit `billingMode`: `QUANTITY` calculates quantity × unit price, and `FLAT_FEE` stores the single amount as canonical quantity `1`, unit price, and server-calculated line total. Existing items default to `QUANTITY`. Issuance verifies flat-fee canonical quantity and amount/line-total consistency before reserving an invoice number. The frozen invoice document loader carries the stored mode to the trusted renderer; flat-fee customer documents hide the internal quantity and unit-price values.

The server-only `src/lib/invoices/invoice-entry-queries.ts` module provides tenant-scoped active client/service searches and a DRAFT-only invoice editing read model. Searches return bounded, deterministic, minimal projections; the edit model uses ISO calendar dates and exact Decimal strings with items ordered by position and ID. These queries do not write database state. `loadDraftInvoicePreview()` separately validates a DRAFT, recalculates exact preview totals, and resolves the latest version of the current active default template without writing or binding it. The issued invoice page and `/pdf` Route Handler use only `loadIssuedInvoiceDocument()`, which reads the frozen version, persisted financials, and issuance snapshots. PDF downloads call `generateIssuedInvoicePdf()` and return private, non-cacheable attachment responses.

Payment recording and invoice supersession are implemented in `src/lib/invoices/record-payment.ts` and `src/lib/invoices/rework-invoice.ts`. Both are server-only transaction services with PostgreSQL integration coverage. Payment records and replacement relations preserve financial history; supersession does not transfer or reverse payments.

Invoice template identities and immutable versions are represented in the database. Issued invoices retain the exact immutable version selected at issuance; historical/manual invoices created before the binding requirement may remain null and require explicit historical handling. `loadIssuedInvoiceDocument()` is a server-only organization-scoped loader for ISSUED, SUPERSEDED, VOID, and WRITTEN_OFF invoices. It uses the invoice's saved `templateVersionId`, renderer key, and config, reads persisted client snapshots and financial values, and never consults the current default template or Client record. `generateIssuedInvoicePdf()` passes this trusted document to the existing PDF generator and derives the filename from the persisted invoice number. Preview and PDF HTML are generated from the same renderer tree and share `src/app/invoice-print.css`; the PDF service prints that output through headless Chromium on A4. The development sample PDF download remains static and separate. Current PDF output is constrained to one page.

Server-side PDF generation is isolated in `src/lib/invoice-templates/generate-pdf.ts` and uses `puppeteer-core`, which does not download or manage Chromium. Production must install Chromium and configure `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` (or the installed executable's absolute path). Run the application as a non-root OS user with Chromium's sandbox usable. DM Sans weights 400, 500, 600, and 700 come from `@fontsource/dm-sans`: the browser preview loads the corresponding bundled weight styles, and PDF HTML embeds the matching fixed Latin WOFF2 files as data URLs. DejaVu Serif continues using the existing host font behavior.

Production create/edit pages keep Preview and Issue unavailable for unsaved drafts. The edit page enables preview and issue for authorized draft editors; unsaved changes must be saved before either action. Issuance confirmation explains the permanent number and frozen date, client snapshot, and template version. On success the browser opens the read-only issued invoice page. Issued pages expose PDF download, with invoice/payment status shown separately. Production PDF reads require `INVOICE_READ`.

The application has a neutral `Hiiiive Billing` placeholder home page and root layout. The development-only invoice preview route remains separate from production invoice data and the fixed development fixture context.

The conventional invoice entry UI lives at `/dev/invoices/new` and `/dev/invoices/[invoiceId]/edit`; both are development-only and return not-found in production. The same responsive form supports create and edit modes. It calls the existing organization-scoped client/service searches, `loadDraftInvoiceForEditing()`, and draft services through development-only Server Actions/server components. An isolated development helper upserts the fixed `hiiiive` organization and deterministic sample client/service; it is unavailable in production. Organization IDs, lifecycle fields, and persisted totals are not read from form input. The form's decimal-string/BigInt calculations are display previews only. New drafts use `createDraftInvoice()`. Full invoice-form draft edits must use `updateFullDraftInvoice()` so the header, client, currency, discount, notes, payment terms, complete item list, and totals commit atomically; the UI must not chain `updateDraftInvoice()` and `replaceDraftInvoiceItems()`.

## Architectural guardrails

- MVP1 serves one organization, Hiiiive. Model organization ownership with `organizationId` so future multi-tenant SaaS use is possible.
- Enforce authentication, authorization, and organization scoping on the server. Every organization-owned lookup and mutation must be scoped to the authorized organization.
- Keep financial calculations, invoice number allocation, approval transitions, and email-send authorization in deterministic server-side code. AI may assist with non-authoritative tasks but never controls these operations.
- Treat issued financial data as immutable. Represent payments and corrections as linked records/events; preserve history.
- Make recurring draft generation idempotent. Separate invoice creation from retryable email delivery.
- Record important actions in immutable audit events.

## Main conceptual flow

A recurring template or an authorized user can create an editable draft. Internal approval and issuance are required before a client invoice can be emailed. Issuance assigns a never-reused invoice number. Payments, supersession/rework, voiding, and write-off are recorded through authorized, auditable transitions without silently rewriting issued financial data. See `BUSINESS-RULES.md` and `DATABASE.md`.
